## 1. P1：分批回放覆盖index，使既有共享库失效

位置：[teacher_replay.py](../sft_new_loop_phase4/teacher_replay.py:342)，`produce`最终只把本次`receipts`写入`index.json`。前面的既有index核验只检查合同/字节，不保证路线集合不缩小，也没有将已完成路线合入本次清单。

在最终v51五路线回放的独立副本上，调用真实`produce`，不替换任何函数、不重算原始帧：

| 操作 | index路线数 | 完整覆盖 |
| --- | ---: | --- |
| 初始副本 | 5 | 是 |
| 同目录请求前2路线 | 2 | 否 |
| 再请求余下3路线 | 3 | 否 |

原路线文件仍在，但index不再指向完整集合。第一步之后，已安装的共享引用由真实`resolve`拒绝，报`production source path/content changed`。这是正确的加载保护，不能通过放宽SHA核验修复。

影响：文档计划的“分批压缩回放”不能直接用同目录不相交`--route-list`实现累计；对已经被数据集引用的完整目录重复子集命令，会破坏该库的可用性。问题不是gzip解码错误，也不是标签变化；原有重写逻辑在共享引用模式下影响扩大。

建议：区分可累计的构建目录与已发布的不可变回放；构建时合并并核验累计receipt、按冻结候选顺序原子发布index，发布后拒绝改变路线集合。若本次不实现分批功能，最低修复是拒绝在已有index目录使用不同路线集合，并在完整回放完成前不建立共享库。补“2+3累计仍5”和“已发布库在子集请求后仍可加载/请求被拒绝且原字节不变”的测试。

复现代码与结果：`checkpoints/v51_code_review_20261012/probe.py`、`probe.json`。原始v51产物没有改动。

## 2. P2：原生总入口尚未统一自动参考准入

位置：[full_pipeline.py](../sft_new_loop_phase4/full_pipeline.py:139)、[train.sh](../sft_new_loop_phase4/train.sh:43)、[preflight.py](../sft_new_loop_phase4/preflight.py:37)。

- `full_pipeline.prepare`在接收外部自动留出之前，就对原生data2调用`require_trainable=True`，配对检查也默认要求原生val/test可训练；纯规则train库加独立自动留出包会提前被空val/test挡住。
- `train.sh`没有把`--selection-mode`和`--teacher-references`传入preflight；preflight本身也没有应用`evaluation_policy.prepare`。因此它检查的人工/混合参考池，与自动模式训练器实际使用的池不同。
- `run_full_pipeline.sh`不会自动导出规则留出；默认训练仍是`reviewed`。人工参考不足十事件时，训练器会正确拒绝，不能把这种拒绝误诊为需要人工逐题补全才能开训。

这不是所有自动入口都不可用：`rgb_short.train`先加载源库，再执行`evaluation_policy.prepare(mode='rule_consistency', references=...)`，重载与评测恢复同一选题合同。**最快路线是固定使用单份原生RGB4库→短视图→自动留出→短视图训练/重载入口**，明确传入规则模式，不必为首轮顺带重写原生双库总入口。若仍要使用原生总入口，则应把相同选择合同接到建库完成判断、preflight和训练，不应删除准入检查。
