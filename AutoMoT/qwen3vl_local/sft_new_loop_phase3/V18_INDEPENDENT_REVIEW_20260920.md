## 1. [P2] 边界诊断无法连接训练过程中生成的验证记录

位置：`audit_label_boundaries.py:91–94`；上游实际记录结构见 `train.py:1052–1077`。

`identity()` 只读顶层 `prompt_road_structure` / `rs`。
训练验证输出把所问道路存入 `prompt_spec.road_structure`，顶层仅有 `true_rs`。
因此同一题在索引中的身份结尾为 `R5`，验证记录中的身份结尾为 `None`，不会连接成功。
`audit()` 仍正常退出，输出空的 `eval_bins`，也不报告有多少输入 case 未匹配。
独立 `eval.py` 的顶层道路字段可以连接，此问题针对训练生成验证记录。

复现使用现有索引的 ControlLoss / Town13_Rep0_1435_0_route0_01_08_10_25_03 / f37，
按 `train.py` 的结构构造一条 `all_ok=True` 的 case：

- 保留嵌套 `prompt_spec.road_structure`：`eval_bins == {}`。
- 仅补上顶层 `prompt_road_structure`：`eval_bins.all.samples == 1`，正确率为 1。

这是数据结构兼容复现，`all_ok=True` 是测试输入，不是模型实测。
建议兼容嵌套的所问道路；不要直接回退到 `true_rs`，错误道路前提题中两者可能不同。
增加 matched/unmatched case 数，并对完全未匹配的非空评测文件明确报错或告警。
回归测试应使用真实训练记录结构，目前测试只覆盖顶层 `rs`。

## 2. [P2] RE5 的 RESUME 场景释义比公共定义更窄

位置：`choice_semantics.py:169`；公共定义见 `prompts.py` 的 `SPEED_ACTION_RULES`。

当前 RE5 写成：

> As the waiting stage ends and a crossing gap opens, gain speed to depart through the junction while monitoring priority traffic.

这把“等待阶段结束”和“空隙打开”并列成条件，但公共定义明确 RESUME 不要求此前停车。
纵向标定也只要求持续增速，不检查是否经历等待；未停车、减速观察后继续加速，或已经在路口内继续增速，
都可以是合法的 RESUME。场景专用说明不应让模型把这些情形理解成不满足 RESUME。

规则层反例：速度序列 `[4, 4.5, 5, 5.5, 6, 6.5, 7, 7.5, 8]`，
`longitudinal_decision()` 输出 `RESUME / first_confirmed_gain`，没有 STOP；
RE5 choice 的 target 也为 RESUME。这是合成的语义反例，不是新增 RGB 错标证据。

建议把可通行空间作为主条件，把结束等待作为一种可能阶段，例如：

> As a usable crossing gap or forward space opens, gain speed to enter or continue through the junction while monitoring priority traffic; this can follow waiting or a slower moving approach.

复看的 RE5 f54 片段中，输入 f51–54 已由 1.290 增至 5.603 m/s，后续继续增速；
它本身仍可解释为此前等待后的离开，不能用它证明“从未等待”。它说明释义需要覆盖已经运动中的持续增速。
两种题型共用该释义，建议一起修订，不改原始速度标定。

## 3. 已确认落实的改进

- 十类 UE/特殊 RE 的动作释义共用一套条件、动作、目的句；目的没有重新放入 scene_context。
- choice 和 binary 都有显式 KEEP；持续等待仍为 STOP，invalid 不补 KEEP。
  判断题中的单项 NO 仍是必要的否定答案，不再承担“整个阶段保持”的正向语义。
- UE2 已完成跨线但事件尚未结束时，可以按当前速度阶段输出 KEEP；发生明确减速时仍应 DECELERATE。
- choice 明确预测主要动作，允许准备减速先于被选中的跨线；binary 明确纵横动作可以先后发生。
  这与现有主要动作优先级一致，但仍不是逐阶段动作顺序监督。
- 两段 UE4 前提不可靠区间已加入精确隔离，测试覆盖边界，不回填 KEEP/NO/invalid。
- 临界 KEEP 使用单独诊断而没有凭个例改变全局速度阈值。

### 5.2 十类场景的条件、动作和目的

以下是本次源码和既有 RGB 记录的交叉核对，不是新增十类全量人工审计。

| 场景 | 当前动作说明已覆盖的联系 |
| --- | --- |
| UE1 前车急减速 | 前向间距缩小→减速保持反应空间；前车阻挡→等待；空间恢复→增速跟随。 |
| UE2 静态障碍 | 受阻→减速避碰并观察邻车/来车/间隙；不能通过→等待；可用间隙→跨线绕行/回归；跨线后仍可保持。 |
| UE3 切入 | 切入压缩前向空间→减速留出位置；空间不足→等待；空间打开→继续推进。 |
| UE4 行人/骑车人 | 接近或占用通道→调速保留通过间隔；不足以通过→等待；包括同向骑车人，不强写成横穿。 |
| UE5 对向侵入 | 路径重叠→减速降低接近速度；通行空间不足→等待；有通过空间时可继续推进，不要求对方完全离场。 |
| UE6 路口违规冲突 | 即使本车有优先权，冲突路径仍要求避碰、判断到达关系和等待清空。 |
| UE7 信号故障 | 故障前提下通过调速观察各进口并判断通行时机；故障事实不靠单帧灯色推断。 |
| RE2 目标换道/恢复 | 按当前导航和可见历史区分出发、等待、跨线、恢复；不固定为已绕完或向右回归。 |
| RE3 合流/驶出 | 调速匹配交通和通过间隙；跨入目标车道与沿既有连接走廊继续行进分开。 |
| RE5 无灯路口 | 依据停止/让行要求等待；允许等待后释放，也允许未停车时持续增速通过。 |

动作选项内部形成连续的条件和目的句，选择题/判断题含义一致。
整体保留必要的规则及选项区块；这不等于模型已经学会这些因果关系。

### 5.3 仍存在的任务边界，不作为新的实现缺陷

1. **标定并未升级成完整的逐阶段工作流真值。**
   原 v8 数值判据和 STOP > 首跨 > 速度的主要动作投影保持不变。
   UE2 开门绕障 f169 的 f171 减速、f176 左跨线，choice 仍为 LEFT，binary 为 DECELERATE:YES + LEFT:YES。
   当前提示词已准确说明该合同，但 target 不包含先后顺序和切换条件。

2. **KEEP 与人的“明显调速”直觉仍可能不同。**
   本轮 1148 条候选中 220 条为主要 KEEP，67 条命中至少一项边界诊断；这些是审查桶，不能当作错标数或错标率。
   UE5 f64 降幅 1.8274578 m/s，距阈值约 0.005985 m/s，仍是速度 KEEP。
   夜间 UE3 f69 后续有速度波动及更晚停车，当前窗仍为 KEEP。
   新文案允许阶段内调速，缓解了解释冲突，但没有消除硬阈值和固定窗口的学习难点。
   模型输入不显示未来数值窗是用户要求，本轮不建议通过重新暴露阈值来掩盖这个边界。

3. **因果目的目前是类别级条件解释。**
   它解释某种动作能帮助什么，但原始标签来自自车速度和车道身份，未逐帧验证驾驶员为何减速、是否在观察间隙、空隙是否安全。
   十类模板已保留相应证据边界，因此不能把通用目的句作为每个样本真实意图的已确认标注。

4. **模型可学习性和全量质量尚未验收。**
   尚无本轮 Qwen 输出、独立新 holdout 或全量生产索引审计。
   后续应在匹配当前合同的评测结果中检查 KEEP/DECELERATE、STOP/RESUME 及准备减速/主要跨线混淆，
   并将临界桶与非临界桶分开观察；不能仅凭单元测试通过宣布提示词效果改善。

本轮人工复看四个既有片段，共 68 个帧面板：UE2 f74（跨线完成后继续通过）、UE2 f169（先减速后借道）、
UE5 f64（近阈值 KEEP）、UE3 f69（波动及窗外停车）。查看前执行异常路线过滤，未扩展 holdout。
旧面板上的 NONE/模型预测是历史叠字，本轮动作以原始 meta 和当前 target 重算，不把叠字当新模型结果。

因此可以确认：用户要求的显式 KEEP、场景事实与动作目的分离、十类因果说明及两种题型一致性已落实；
“所有标定都已完善、每帧因果真实且模型都能学会”的更强结论目前没有证据支持。
