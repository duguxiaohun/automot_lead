# Phase3 v12：默认四帧单选与场景目的

采用 v11 的紧凑 prompt、v10 数据规则与 v8 bounded-window 标定，默认新训
`4rgb + choice`，两帧/binary 保留显式 demo。v11 四帧 choice test 为 581/762（76.25%），
双帧 choice 为 589/762（77.30%），仅作为历史参考；
v12 加了场景目的，必须重新训练，不能沿用该成绩或称为已验证最终模型。

## 本次变化

目的只由当前提出的 context 决定，写在 `[SCENE_CONTEXT]` 下，注明前提成立时才适用。
每题只显示一条，不额外要求模型生成解释。UE1 指向跟车间距和前车冲突；UE2 指向
观察相邻车道交通、接近车辆、借道时的对向来车及侧向通过空间，判断绕障空隙。
RE2 检查目标车道的车辆/空隙，恢复必须有先前离开车道的证据；RE3 关注汇入/目标
车道车辆的位置与相对运动。其余场景分别解释切入让空间、保护行人/骑行者、等待
对向侵入者或路口冲突者通过、灯故障时观察冲突交通，以及无灯路口遵守优先权。

所有描述都是条件性动机，不宣称存在可见空隙，不读取未来轨迹/答案，不指定左右方向，
不把减速推成马上变道。原速度阈值、STOP 优先级、首次跨线时间窗、动作名、
单选候选随机顺序及严格 parser 保持原样。binary 也共享这句目的。

## 数据与评测边界

`trajectory_action.py`、`context_taxonomy.py`、映射决定、人工审计记录、划分 seed 均未修改。
源码合同包含 prompt/default 文件，因此哈希变化要求 pipeline 重建独立
`checkpoints/sft_new_loop_phase3_data_v12`；这不是重新人工标定，不覆盖旧 v11 索引。
沿用自动一致性检查，不安排新的逐帧 RGB 人工审计。

choice 仍只训练/评测唯一正动作且有效的样本；NONE、invalid、多动作保持显式剔除统计。
这不等价于 action_prior 的 binary 多标签动作输入，本次不修改 action_prior。
validation 继续选 `best_generation`，历史 step 6000 不固定成选优条件；若只获得
final/fallback，按实际 slot 报告，不把它标成通过质量门槛的 best。
沿用同划分便于开发对照；test 已参与版本选择，本轮不得称为全新独立测试。

新训练与 base eval 默认四帧 choice；LoRA eval 仍读取保存合同并拒绝显式错配。
旧缺字段配置回退语义保持四图 binary，但仍受原 prompt/hash 校验，不能在新代码中混跑。
底层多标签 API 的默认 binary 保留，避免改变现有标签/诊断调用。
具体命令见 [SFT_NEW_LOOP_PHASE3_RUN.md](SFT_NEW_LOOP_PHASE3_RUN.md)。

## 本地验证

目的渲染、答案独立性、四种模式 hash 失效、实际 CLI 默认值/显式覆盖、旧 adapter
模式回退，以及原时间窗/动作/解析合同共 101 项 CPU 回归通过，3 项依赖 torch 的测试未运行。
Python 编译、四个 shell 入口语法及 `git diff --check` 通过。本地缺 torch，未进行真实
Qwen 训练、生成或新索引全源构建；上述检查不证明准确率提升。
